## Context

动机和用户确认见 proposal.md。当前 WPF App 已显示程序集版本，维护菜单可添加更新入口。`LauncherViewModel.SessionState` 区分 Idle、Active、Stopping、StopFailed、Closing；登录完成后仍是 Active，不能以 `IsBusy == false` 作为可升级依据。

现有构建入口生成完整自包含安装包、SHA256SUMS 和 schema v1 清单。安装器重新绑定主程序及三个 DLL 到认证组件，支持交互式覆盖升级和失败恢复；拒绝静默安装。源码版本源为 `build/version.json`，现有发布记录仍有干净电脑实装验收待完成。仓库公开，目前无 Release 或 Actions 发布流程。

## Goals / Non-Goals

**Goals:**

- main 每次 push 的最终提交触发完整验证与发布，无需人工修改补丁号或手传安装包。
- 客户端启动后后台检查一次，也能手动检查；用户决定下载和安装，业务期间不强制退出。
- 更新过程保留用户数据，复用整个安装器，清楚区分检查、下载、安装与实际安装成功。

**Non-Goals:**

- 不保证提交后立即可下载，需等待测试、构建、上传；不做持续秒级轮询。
- 不在客户端拉取或编译 Git 工程，不只替换 App.exe，不在进行中的银行业务内热替换。
- 不做静默提权、差分更新、预览版通道、多用户安装或 GitHub 私有仓库凭据分发。
- 不将现有安装器尚未完成的实机验收视为已通过。

## Decisions

### 1. 固定仓库提供完整正式版本

发布源固定为 `yxsimony-dot/CCB-USB-User`。使用 GitHub Releases 承载安装 EXE、release-manifest.json 与 SHA256SUMS。客户端匿名读取公开资源；GitHub 写入令牌只在受信任发布任务中使用。

比较过直接下载源码、本地编译以及仅打开浏览器下载页。整包下载并调用现有安装器能复用版本、绑定、恢复和用户数据保留契约，也符合应用内更新的目标。

### 2. 自动版本，不生成机器人提交

给构建入口增加显式发布序号参数。基础版本继续来自 `build/version.json`，CI 实际版本为 `major.minor.(basePatch + github.run_number)`；发布该功能时基础版本进入 1.1 系列。普通本地构建使用基础版本，也可显式提供序号重建发行版本。

一次构建只解析一次有效版本，并统一传给 MSBuild、Inno、载荷 product.json、UI 与清单。不修改已跟踪的版本文件来伪造干净源码；不向 main 写机器人版本提交。有效版本各段必须不超过 65535，不支持回绕。

清单保留已有 schema v1 必填字段，增加可选的 baseVersion、releaseSequence、workflowRunId、workflowRunNumber、workflowRunUrl。`sourceCommit` 和 Release tag 均绑定本次 push 的不可变 SHA；`sourceDirty` 必须为 false，构建前后检查受跟踪输入未被修改。同一 run 重跑保持版本和 run identity，attempt 可变但不参与版本号。

基础版本不得回退；工作流重建导致计数重置、版本碰撞或较高序号映射到不高于此前版本时停止并报告配置问题。允许旧 run 晚完成发布其原有低版本，不把乱序误判成配置回退。校验须结合 run number 和既有发布身份，而非一律拒绝低于当前最高版本的发布。

### 3. 每次 main push 的发布流水线

工作流仅由目标仓库 main push 触发，包含仅文档更新的推送；一次 push 包含多个 commit 时构建其最终 SHA。重跑使用 Actions 原有 run，不允许任意旧 SHA 作为新的更高版本发布。

固定 Windows runner 系列及已验证 SDK/Node/Inno 工具版本，复用构建入口执行锁定恢复、非硬件测试、浏览器测试、安装事务测试、干净发布、载荷验证和编译。工具下载需核对来源/散列或已验证签名，不能信任任意下载脚本。第三方 actions 固定提交；测试/构建使用只读权限，发布任务才获得 contents:write，PR 不获得发布权限。

各 push 使用独立版本/tag 并行构建发布，不配置会取消旧等待项的全局并发组。仅针对同一版本防止同时写入。失败构建保留诊断，不创建正式 Release。

发布顺序为：构建成功 → 创建/恢复同身份草稿 → 上传三个文件 → 重新读取并核对远端资产完整性和散列 → 公开正式 Release。草稿与预发布不进入客户端更新列表。

匹配同 SHA、版本、产品和 run identity 的草稿可以恢复；同版本正式 Release 已存在且远端资产完整时直接视为幂等成功，不覆盖既有文件，也不要求重新编译产生的带时间戳 EXE 与旧文件字节相同。tag 指向、身份或远端校验冲突时失败，不覆盖。晚完成的旧版本不得使客户端回退；GitHub 的 latest 标记仅供网页展示，客户端不依赖该标记。

### 4. 更新发现与界面

在维护菜单增加“检查更新”。启动时后台检查一次，用非阻塞状态提示有新版；不自动下载、不弹安装器、不影响 Key 检测或页面初始化。用户主动检查显示完整状态：正在检查、已是最新、发现新版、暂无已发布版本、无法连接/限流、版本不兼容或发布文件异常。

通过分页 Releases API 获取正式稳定版，以三段数字版本比较，校验候选 tag、清单版本、产品、仓库、平台、架构、清单 schema、资产名/大小和源提交，选择最高有效兼容版本。不可按字符串排序，也不可仅取最新发布时间。高版本损坏或不兼容须可见，不误报已是最新；可显示更低但仍高于本地的有效更新作为可用候选，并说明更高版本不可用。

检查服务与 UI 状态隔离，使用可取消 HTTP、超时、分页/响应大小上限和合并重复请求。可缓存 ETag 降低匿名限流；未完成所有必要分页时不能把部分结果报告为完整最新结论。关闭窗口或应用后不回写旧状态。更新说明按普通文本展示，不执行远端 HTML。

### 5. 下载与安装交接

用户确认后下载到当前用户 `%LOCALAPPDATA%/UsbWebLauncher/updates/<version>`，不放进安装目录或银行 PDF 目录。先写临时文件，限制实际下载长度，校验清单大小和 SHA-256 后才成为可安装文件。取消、超时或校验失败清理该次部分文件，保留当前版本。下载 URL 必须关联已选择 Release 的资产，验证 HTTPS、官方 GitHub 资产主机及重定向，不采用任意清单执行路径。

SHA-256 用于完整性检查；目前未签名包仍明确标为未签名，不声称经过发布者签名验证。执行前复核落盘文件和版本身份，防止陈旧或被改动的缓存被误用。

用户点击安装时再次确认 `SessionState == Idle` 且无导出/停止/关闭正在进行，并锁定新的业务启动入口直至交接结束。非空闲提示先“中止业务”；下载期间 Key 拔插不触发安装。启动安装包保持普通用户权限，让既有安装器按需要申请 UAC，然后走现有有时限的正常退出流程。

启动安装器失败时恢复应用按钮状态并显示错误。成功启动只表示已交接，不提前显示升级完成。用户取消安装后仍可从原入口运行旧版并重试；真正升级失败由安装器恢复/保留事务。安装完成后从开始菜单或完成页打开新版，显示新版本且不自动进入银行业务。开发/publish 目录运行时说明更新安装到固定目录，不覆盖任意开发目录。

### 6. 首个带更新能力的版本

用户已同意 1.0.0 手动安装一次。交付新安装包及正式 Release 入口，之后同一安装用户即可在应用内更新。发布前运行合成 HTTP/安装回调测试；真实验收覆盖本机原安装 → 新安装、PIN/目录/PDF 保留、取消 UAC/安装、在业务中请求更新以及失败恢复。未经实际执行的项目保留未验收。

## Risks / Trade-offs

- [main 中每次变动都会发布] → 按用户选择执行，自动测试是发布门槛；发布权限限定可信 main 工作流。自动测试不能证明银行硬件场景全部可用。
- [GitHub 网络、限流或服务中断] → 超时、取消、明确错误、手动重试；当前业务仍可使用。
- [乱序构建或重跑] → 不可变版本/run/source 绑定、先草稿后公开、正式资产不覆盖、客户端数字版本选择。
- [版本序号超出 Windows 范围或重置] → 构建前停止，显式调整基础版本，禁止版本回绕和覆盖。
- [认证组件与主程序不一致] → 整包安装并复用健康检查/恢复，不自行覆写运行文件。
- [现有包未签名、干净机尚未验收] → 如实保留签名状态和验收记录，不承诺静默无提示或任意电脑兼容。

## Migration Plan

先实现版本解析、发布协议与更新客户端的替身测试，再接入 UI/业务状态和安装交接，随后配置 main 工作流。开启工作流即会使后续 main 推送自动发布，属于已确认的产品行为。首次实际发布核对远端三个文件和无凭据客户端读取，再交付首次手动安装包并执行受控升级验收。

发现错误版本时可撤回该 Release，客户端停止推荐；已安装用户不自动降级，应修复后发布更高版本。任何恢复不删除 PIN、设置或银行 PDF。
